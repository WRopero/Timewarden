#### Dataform profile
- **Structure:** `workflow_settings.yaml` (or `dataform.json`: `defaultProject`, `defaultLocation`, `defaultDataset`, `defaultAssertionDataset`, `dataformCoreVersion`), `definitions/` (source declarations `type: "declaration"`, staging, intermediates, marts) and `includes/` (JS constants and functions). Always reference with `${ref("...")}` / `${resolve("...")}`; never hard-coded `project.dataset.table`.
- **Compile before running:** `dataform compile` is free and catches cycles/broken refs. To run use `dataform run --dry-run` or specific `--actions`; **never run or reschedule production workflows (release/workflow configs) without explicit approval**.
- **Environments:** separate dev/prod by GCP project or with `schemaSuffix`/`tablePrefix` and compilation `vars`; never write to production datasets from a development workspace.
- **Quality:** use `assertions: { nonNull, uniqueKey, rowConditions }` on every relevant table and manual assertions for business rules; failing assertions are investigated, not removed.
- **Incrementals:** `type: "incremental"` with `uniqueKey` and `updatePartitionFilter`; a full refresh (`--full-refresh`) on large tables needs approval (bytes processed cost and data window).
- **Versions and security:** `@dataform/core` pinned in `package.json`/`dataformCoreVersion`; security bumps are recorded by naming the CVE/GHSA in the commit. Service-account credentials stay out of the repo (ADC / the Dataform service identity).
- **Deployment:** "deployed" = the release config compiled that commit **and** the production workflow config finished OK. Record it with `memory_deploy.py record <env>` only after verifying. Keep in memory: grain, partitioning/clustering, owner and SLA of each table, and the bytes-per-run baseline.
